## Критичное (проверяющий может не пройти сценарий)

1. **Хост API зашит при сборке, и это шард `4100`.** В бандл на Pages попал `https://4100.api.green-api.com`. У GREEN-API `apiUrl` свой у каждого инстанса (он показан в консоли), поэтому инстанс проверяющего на другом хосте не заработает. Лучше добавить в форму поле `apiUrl` с дефолтом. `src/config/runtime.ts`, `.github/workflows/deploy-pages.yml:37`
2. **Входящее сообщение может потеряться навсегда.** Пока не ответил `getContactInfo`, `contactChatId` не определён. Если у собеседника скрыт номер (`senderPhoneNumber === '0'`), сообщение отбрасывается, а его уведомление всё равно удаляется из очереди. Если `getContactInfo` упадёт, ошибка молча проглатывается, и так будет со всеми входящими до конца сессии. `useNotificationPolling.ts:164-166`, `useChatContact.ts:40`
3. **Показываются только сообщения с `typeMessage === 'textMessage'`.** Ответ в Telegram через «Ответить» (`quotedMessage`) или текст со ссылкой (`extendedTextMessage`) молча удаляются из очереди. Как раз «получатель отвечает» из сценария может не отобразиться. Это нужно проверить на реальном инстансе. `useNotificationPolling.ts:161`

## Баги и неточности

4. **Неверный лимит длины: 4096 вместо 4000.** В документации SendMessage указано максимум 4000 символов. `ChatWorkspace.tsx:116,120,168`
5. **Время входящего сообщения берётся из `Date.now()`, а не из `timestamp` уведомления.** Бэклог очереди (уведомления хранятся до 24 ч) при открытии чата показывается как свежие сообщения с текущим временем. `ChatWorkspace.tsx:54`
6. **`deleteNotification` с `result: false` полностью останавливает polling (`terminal`).** Так бывает, если квитанцию уже удалил кто-то другой. Здесь достаточно пропустить её и читать дальше. `useNotificationPolling.ts:99-100`
7. **При подключении учётные данные не проверяются.** С неверным токеном чат откроется, а ошибка появится позже и только в виде «получение остановлено». Можно дёрнуть `getStateInstance` на сабмите формы.
8. **Кнопка «назад» стирает всё.** Возвращает на пустую форму: ID, токен и история теряются, и для нового чата всё нужно вводить заново. Сценарий «создать новый чат» из-за этого неудобен.
9. **Клиент API создаётся заново при каждом рендере `App`.** Он указан в зависимостях эффектов polling и contact, поэтому любой ререндер `App` перезапустит поллинг. Сейчас это не стреляет, но хрупко. Нужен `useMemo`. `App.tsx:32`
10. **Отправляется нетримленный `draft`, хотя проверяется `draft.trim()`.** Уходят лишние пробелы и переводы строк по краям. `ChatWorkspace.tsx:116-117`

## UX относительно «как в Telegram»

11. **Enter не отправляет сообщение**, работает только кнопка. В Telegram Enter отправляет, а Shift+Enter переносит строку.
12. **Пока предыдущее сообщение не отправилось, следующее отправить нельзя** (`isSending` блокирует форму).
13. **Номер без «+» (`79001234567`) не распознаётся:** без выбранной страны форма выдаёт ошибку. Проще подставлять «+» автоматически.
14. **Нет списка чатов,** работает ровно один диалог. Для «минимального» задания это допустимо, но стоит одной строкой упомянуть это в README как осознанное решение.

## Репозиторий и документация

15. **README ничего не говорит о переменной `VITE_GREEN_API_URL` (Settings → Variables).** Без неё форк соберётся в экран с ошибкой конфигурации.
16. **Про Node.js в README неточно.** Там написано «Node.js 20+», но Vite 7 требует 20.19+ или 22.12+.
17. **Решение перегружено для задания «максимально просто»:** комбобокс стран с флагами с внешнего CDN (`flagcdn.com`), аватары, 5 статусов, retry, state-машина очереди. Код плотный: многие JSX-строки длиной 150+ символов (`App.tsx:32`, `ChatWorkspace.tsx:160-161`).
18. **`docs/plans/*` и `docs/solutions/*` с метаданными `artifact_contract: ce-unified-plan/v1` и коммиты `U5…U11` выглядят как вывод AI-агента.** Если это не нужно показывать работодателю, лучше убрать.
